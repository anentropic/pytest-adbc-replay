```python
def adbc_clone(self) -> ReplayConnection:
    """Create a cloned connection sharing the same cassette and config."""
    real_clone = self._real_conn.adbc_clone() if self._real_conn is not None else None
    clone = ReplayConnection.__new__(ReplayConnection)
    # ... copies all config attributes ...
    clone._cassette_path = self._cassette_path  # shared reference
    clone._wipe_state = self._wipe_state         # shared mutable dict
    return clone
```

Create `docs/src/explanation/connection-pooling.md` following the pattern from `record-mode-semantics.md`.

Title: "Connection pooling and replay"

Structure:
1. Intro paragraph: "This article explains how pytest-adbc-replay handles connection pooling, why clones share cassette paths and wipe state, and what happens when concurrent access is attempted."
2. "## Why clones share the cassette path" section:
   - Design rationale: a pool connection is logically the same database session. All queries from any pool checkout should be recorded to the same cassette directory because they belong to the same test.
   - If clones had separate cassette paths, the cassette directory structure would fragment unpredictably based on how many pool connections were checked out.
3. "## Pool replay lifecycle" section:
   - Full walkthrough of what happens at each stage. Use prose or a mermaid diagram (Claude's discretion, but a mermaid sequenceDiagram or stateDiagram-v2 is recommended):
     1. Source `ReplayConnection` created (via `adbc_connect` or `adbc_replay.wrap()`)
     2. Pool library calls `source.adbc_clone()` to create checkout connections
     3. Each clone gets its own cursor via `clone.cursor()`
     4. Cursor executes queries -- records to or replays from the shared cassette path
     5. Pool disposes -- clones closed, source closed
   - Explain that in record mode, the real ADBC connection is also cloned (`self._real_conn.adbc_clone()`). In replay mode, clones have `_real_conn = None`.
4. "## Shared wipe state" section:
   - In `all` record mode, the first cursor to call `execute()` across ALL connections (source + clones) wipes the cassette directory via `shutil.rmtree()`
   - The wipe state is a shared mutable dict `{"wiped": False}` referenced by source and all clones
   - After one cursor wipes, all subsequent cursors see `wiped = True` and skip
   - This prevents later pool connections from destroying earlier recordings
5. "## Concurrent access and its failure mode" section:
   - Replay queues are per-cursor, not shared across clones
   - Each cursor loads all cassette interactions into its own deque on first `execute()`
   - If two cursors from different clones execute concurrently (e.g. in multi-threaded test code), each pops from its own independent queue
   - This can lead to wrong result matching: the pop order depends on thread scheduling, not query identity
   - In typical single-threaded pytest runs, cursors execute sequentially and this is never a problem
   - This is a known limitation, not a bug -- the sequential access model matches how most test code works
6. "## ADBC spec context" section (brief):
   - `adbc_clone()` is an ADBC extension (not DBAPI 2.0)
   - Creates a Connection sharing the same underlying AdbcDatabase
   - Link to ADBC Python API docs
7. Links at bottom to:
   - How-to: Use with connection pools (../how-to/connection-pools.md)
   - Reference: Connection Pooling (../reference/connection-pooling.md)
